## 3. 识别算法

```
帧 → 灰度 → 局部对比找卡片 → 卡内 Otsu 二值化 → 连通域
   → 过滤（面积/长宽比/贴边）→ 28×28 归一化（20px 贴合 + 质心居中）
   → 784-256-10 前馈网络 → 数字 + 置信度
```

关键点：

- **卡片定位用局部对比**（`box_blur` 均值滤波 + 差值门限 12），不用全局 Otsu。
  全局阈值在“地板占 95%、卡片占 5%”时会去切地板自己的明暗，卡片整个丢失。
- **归一化必须对齐 MNIST 的几何**：先缩到 20×20 内，再按质心放进 28×28。
  否则模型看到的输入分布和训练时不同，准确率会掉一大截。
- 找不到卡片时退回全局墨迹检测；检测不到任何数字 → 返回空串（播报“看不清”）。

## 6. 判读规则（给播报用）

- 一致性 = 表决通过的帧数 / 总帧数；默认要求 ≥ 0.60
- 单字置信度 < 0.60 → 播报“我看不太清，能再让我靠近一点吗”
- 多数字（>1 位）时按从左到右拼接，仅支持 1–4 位

## 7. 已知限制

- 手写体风格与 MNIST 差异大时（连笔、倾斜很大）会误识；演示建议用**工整、笔画分离**的写法。
- 强反光、卡片褶皱、字迹太细（< 3 mm 笔画）都会降低准确率。
- 目前只支持 0–9 单字符到 4 字符，不做两位数的语义校验。

## 8. 笔的颜色（实测）

链路是灰度处理，**色相不重要、亮度对比才重要**。同一套场景管线换墨色各跑 80 次：

| 墨色 | 端到端准确率 | 认错 | 没检出 |
|---|---|---|---|
| 黑笔 (30) | 96.2% | 0 | 3 |
| 蓝笔 (40,60,190) | 96.2% | 0 | 3 |
| 红笔 (200,35,35) | 96.2% | 0 | 3 |
| 铅笔 (120) | 96.2% | 0 | 3 |
| 浅铅笔 (155) | 96.2% | 0 | 3 |

结论：**颜色完全不影响**（灰度只看亮度差）。加自适应阈值后五种墨色已无差别，剩下的 3 次全是"没检出"而不是"认错"。
仍建议笔画粗一点（马克笔最佳）、白纸；避免彩色纸。

## 9. 低对比度字迹（薄红笔 / 铅笔）为什么现在能读

首张真机卡片是**笔记本纸 + 很薄的红笔手写 "2"**，旧管线读出空。逐层定位后改了三处（均在 `host/app/vision/digit_reader.py`）：

| 问题 | 现象 | 改法 |
|---|---|---|
| 卡内全局 Otsu 被纸边阴影支配 | 阈值 162，字（≈175）根本不算"墨" | 新增 `adaptive_ink_mask`：比 20 px 邻域均值暗 6 级即算墨；卡内先自适应、再退回 Otsu |
| 卡片框只框到纸的**边缘对比**处，右边被切掉 1/3 | 字被裁掉，或把纸边阴影当成数字 | 卡片框外扩 30%（`pad = 0.30*min(w,h)`）；只有裁剪边同时也是**画面边**时才允许贴边 |
| 外扩后地板砖缝/椅子阴影被读成 "4" | 读出 "22" | 宽高比下限 0.25→**0.5**；组件**至少 50% 落在卡片框内**（`_mostly_on_card`） |

改完实测：真机卡 3/3 帧读作 `2`（conf 0.69–0.74，agreement 1.00）；
场景基准 200 张 **195 对 / 3 错 / 2 未检出（97.5%）**；回归 170 项全过。
证据：`metrics/evidence/digit_20261026T201131.png`、`_scratch/frame_card.jpg`。

## 10. 笔记本纸 + 蓝笔 "7" 的第二轮修复（2026-10-26 20:18）

同一场景 6 帧里有 2 帧 `find_card` 返回空（卡片贴在画面底边，纸边对比不足），
并且笔记本的**装订孔/页角**被当成一个 24x23 的小字（分类成 6/2/8 抖动），于是出现
`'87'`、`'27'` 这种多读一位的结果。两处修正：

| 问题 | 改法 |
|---|---|
| 连拍中个别帧找不到卡片 | `read_digits(..., card_hint=)` 接上一帧的好框；`tools/digit_live.py` 在连拍内维护 `last_card` |
| 小于字迹尺寸的杂物被当成数字 | `_big_enough_on_card`：字高须 ≥ 卡片高的 25%、字宽 ≥ 卡片宽的 10% |

改完：同场景 6/6 帧读作 `7`（conf 0.94–0.96）；连拍 4/4 帧一致；
基准不变（场景 97.5%、五色各 96.2%）；回归 170 项全过。
证据：`metrics/evidence/digit_20261026T201818.png`。

## 11. 卡片与地板"同亮度"时的兜底（2026-10-26 20:27）

把纸挪到光照均匀的位置后，纸面亮度 182、周围亮地砖 191 —— **纸并不比地板亮**，
靠边缘对比的 `find_card` 正确返回 None，于是读不出。人类靠纸的**边界轮廓**认，
而这在纯亮度特征里几乎没有信号。

新增两级兜底（`host/app/vision/digit_reader.py`）：

| 层级 | 做法 | 适用 |
|---|---|---|
| 1 | `find_card` + 卡内自适应阈值（原路径） | 卡片边缘能看出来（多数情况） |
| 2 | `_roi_glyph`：只看**画面下方 58%~100%、水平 20%~85%** 的近场地面，取最大的数字状暗块 | 纸与地板同亮度、但字仍是近场唯一的大暗块 |
| 3 | 全帧 Otsu | 兜底 |

第 2 级只保留**最大**的一个块（按外接框面积），因为读卡片就是读一个字；椅子腿/瓶标
要么过长、要么远离近场。

### 笔画加粗（决定性的一步）

薄笔墨画在纸上只有 1–2 px 宽，而 MNIST 的字是粗的；把细线缩放到 20 px 还是细线，
分类器就在 3/8、2/7 之间犹豫。加 `_dilate(..., STROKE_DILATE=2)`（4 邻域两遍）后，
真机三张卡的置信度从 **0.64–0.67 → 0.87–0.99**，而场景基准**一格没变**。

### 这一步之后

| 卡片 | 结果 |
|---|---|
| 簿纸+薄红笔 "2" | `2` conf 0.95 |
| 簿纸+蓝笔 "7" | `7` conf 1.00 |
| 白纸+深笔 "3"（新位置，纸与地板同亮度） | `3` conf 0.97–0.99，连拍 4/4 |

基准不变：场景 200 张 195 对/3 错/2 未检出（97.5%）；五色笔各 96.2%、认错 0；170 项测试全过。
证据：`metrics/evidence/digit_20261026T202705.png`。

已知限制：兜底路径假定近场只有**一个**数字；卡上多字时会只取最大那个。

## 12. "手举笔记本"场景：把杂物挡在外面（2026-10-26 20:40）

用户把笔记本举到镜头前时，`find_card` 返回 None，近场兜底把**袖子/手臂**当成一个字，
读出 `'7'`（conf 0.999）与 `'8'`（conf 0.96）——**自信地读错**，这是最危险的失败模式。

### 判据：字周围那一圈应该"像纸"

`_ring_stats(gray, box, pad=12)` 取框外 12 px 环的中位数 / 标准差 / 10-90 分位差：

| 场景 | 环中位数 | 标准差 | spread | 结果 |
|---|---|---|---|---|
| 簿纸红笔 "2" | 196 | 6.6 | 17 | 保留 |
| 蓝笔 "7"（贴画面底边） | 77 | 4.3 | 12 | 保留 |
| 白纸深笔 "3"（纸=地板亮度） | 172 | 19.6 | 40 | 保留 |
| **手举笔记本（袖子入镜）** | 117 | **42.9** | **123** | 丢弃 |

`MAX_RING_STD = 30`、`MAX_RING_SPREAD = 80`：两个条件**同时**超标才判杂物。
全局 Otsu 兜底也走同一过滤器，否则被 ROI 拒掉的袖子会在全局路径被重新捡回来。
读不到就说"没看到数字"，**绝不猜**。

### 笔画加粗改为"按需"

固定膨胀两次会让粗笔/MNIST 风格的字过度加粗，合成场景从 195 掉到 193。
改为按字形填充率自适应（`_stroke_passes`）：

| 填 充 率 | 膨胀次数 | 典型对象 |
|---|---|---|
| < 0.16 | 2 | 圆珠笔细线 |
| 0.16–0.26 | 1 | 中性笔 |
| > 0.26 | 0 | 粗记号笔 / MNIST |

结果：合成场景回到 **195/3/2（97.5%）**、五色笔各 **96.2%（认错 0）**，
而真机三张卡仍是 0.95 / 1.00 / 0.98，杂物帧正确拒识。

证据：`metrics/evidence/digit_20261026T204009.png`（红笔 "2"，0.99）、
`metrics/evidence/digit_20261026T203200.png`（杂物帧，读出空）。

## 13. 速度优化：组件标注改用 scipy 快路径（4.4x）

`find_card` 原来 147 ms，profile 显示其中约 199/233 ms 花在 `_components`
（纯 Python 逐像素 union-find，一帧 5 万多次 `find`/`union`）。真实帧读出
需要连拍 3 帧，于是单次读卡要 0.6 s 以上，体感很慢。

改为：`_components()` 在能 import scipy 时走 `scipy.ndimage.label`（C 实现），
否则退回原来的 union-find —— 两条路径**语义完全一致**，都返回半开区间
`(x0, y0, x1, y1, area)`（`x1`/`y1` 是 exclusive，与调用方的 `gray[y0:y1, x0:x1]`
一致）。第一条 scipy 实现忘了减一/加一，卡片裁剪少一行一列，`bench_scenes`
从 195 掉到 194；对齐后恢复 195。

| 指标 | 优化前 | 优化后 |
|---|---|---|
| `find_card` | 147 ms | 34–44 ms |
| 单次 `read_digits` | 210 ms | 43–47 ms |
| `bench_scenes` | 195/200 | **195/200**（不变） |
| `bench_ink` 五色 | 96.2% / 0 错 | **96.2% / 0 错**（不变） |
| `bench_stress` | 33/52 | **33/52**（不变） |
| pytest | 258 | **260**（新增两条 parity 测试） |

新增回归测试锁死「两条标注器必须逐框相同」与「框是半开区间」，
避免以后换实现/加优化时静默改掉裁剪尺寸。

## 14. 现场三条铁律（2026-10-27 真机走读总结）

这节只写"照着做就不会错"的东西，全部来自当天真机。

### 14.1 背景比算法重要：棕色硬纸壳 + 白纸

无边框白纸放在浅色地砖上时，`find_card` 的检出率只有 **1/5 帧**，而且会把框画到
旁边的黑鞋上（`metrics/evidence` 外的调试图 `_scratch/boxed.png` 可复现）。
改 `find_card` 的亮度判据（相对中位数、80 分位）只会让"暗物 + 地板"的框更容易通过，
**试过两版都更糟，已回滚**——`min_brightness=160` 的绝对判据不能动。

正确做法是把**背景**换掉：棕色硬纸壳铺地、白纸居中。同一位置
`digit_live --shots 5` 立刻 4/5 读出 `3`（agreement 0.80），换成粗黑马克笔后 **5/5、
置信度 0.98–0.99、三帧一致度 1.00**。

> 一句话：**这是视觉的活，不是分类器的活。** 现场摆放（背景、笔）比调阈值省事十倍。

同一晚还补了一条判据：纸必须**比它躺着的背景亮**（`find_card(min_contrast=25)` 灰阶）。
起因是扫视时把"地砖缝围出来的一块亮地板"当成卡片——框贴画面底边、框内只比周围亮 **12**
灰阶，对准走近折腾半天，读出来必然 `empty`。真卡在棕色纸壳上是 **+86**，两者不重叠。
所以**卡片下面必须垫比纸暗的东西**：纯地砖上放白纸即使勉强检出，也会被这条判据滤掉。

### 14.2 笔必须是粗黑马克笔

铅笔细线会让分类器**自信地读错**：同一张写着 `3` 的纸，铅笔笔画读成 `5`，
置信度 **0.995**、三帧一致度 1.0——比"读不出"更危险，因为它会照样播报。

要求：马克笔/白板笔，笔画约 1 cm，字占纸面一半以上。铅笔、圆珠笔、细中性笔一律不要。

### 14.3 停多远：卡片宽度 120 px

`find_card` 框宽就是距离的替身（同一张卡，越近越宽）：

| 框宽 | 结果 |
|---|---|
| 86–106 px | 检测到但没有字形，读 `""` / `empty` |
| **124–129 px** | 稳定读出，置信度 0.97+ |
| 320 px 以上 | 字形出画，停止前进 |

所以自动靠近的停下阈值是 **120 px**（`tools/voice_agent.py` 的 `APPROACH_TARGET_PX`，
也可用 `--approach-px` 调），最大 320 px 硬停。真机一次：86→94→106→**129 px** 自己停，
读出 `3` @0.972。

### 14.4 每次停下来之后，第一条运动指令会被丢掉

真机 4 次全部复现：**发过停止帧后狗会丢掉我们的速度流**，必须重新发一帧
`0x21010C03`（自主模式）才再动。脚本里统一处理成"没走到 0.02 m 就以模式码重发 + 重试一次"
（`tools/turn_check.py --rearm`、`_scratch/*.py`、`tools/voice_agent.py` 的靠近流程）。

顺带：手柄随时会抢控制权（`docs/mode_protocol.md` H2），人一碰手柄就表现为
`dog is not responding`，这时按 `0x21010C03` 抢回来即可。

## 15. 停稳再拍：连拍挑帧 + 逐帧质量门（2026-10-28 晚）

第 3 项验收之后又踩到一个坑：**糊掉的卡片不会被"看不见"，而是被"自信地读错"**。
用一张确认是 `3` 的实拍图做高斯模糊梯度（同一套代码，同一个分类器）：

| 模糊半径 | 0 | 2 | 4 | 6 | 8 | 10 | 12 |
|---|---|---|---|---|---|---|---|
| 能否检出卡片 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| 读出结果 | `3`@0.98 | `3`@0.93 | **`2`@0.99** | `2`@0.71 | `3`@0.82 | `1`@1.00 | — |
| 卡片 ROI 的拉普拉斯方差 | 1495 | 10.3 | 2.3 | 1.9 | 1.9 | 2.0 | — |

两件事同时成立：**检测器能撑到半径 11，识别器半径 4 就崩**，而且给出 0.99 的置信度。
所以"多拍几帧投票"救不了它——三张糊图会**一致地**投出同一个错误答案。

### 15.1 做法

`host/app/vision/frame_quality.py`：每帧打分，四项硬门槛 + 一个排序分。

| 门槛 | 值 | 依据 |
|---|---|---|
| 卡片宽度 | ≥ **110 px** | 86–111 px 读不稳，124–143 px 稳定 0.97+ |
| 拉普拉斯方差 | ≥ **120** | 清晰帧 1300–1800，半径 4 的糊帧只有 ~2（三个数量级分离） |
| 卡片对比度 | ≥ 25 | 与 `find_card` 的 `min_contrast` 同源，防地砖假阳性 |
| 框底贴边 | 不允许 | 太近时卡片被画面下沿切掉，字读成 `empty` |

`digit_service.read_burst(shots=4, gap=0.15)`：连拍 4 帧 → 打分 → **只对过关的帧投票**
→ 一帧都不过关就返回 `reason="blurred"`，播报「有点糊，我再看一眼」，**不猜**。
`read_settled` 在外面再包一层（静止 1.5 s + 不确定重拍一次）。

真机（无狗移动）实测：4 帧 0.63 s；用三张实拍图模拟：

```
全清晰      -> digits=3 conf=0.984 agreement=1.0  shots=3  ok
两糊一清晰  -> digits=3 conf=0.984 agreement=1.0  shots=1  ok      # 糊帧被丢弃
全糊        -> digits=""                    shots=3  blurred       # 不再是 0.99 的错读
```

### 15.2 顺带：曝光可以钉死（但默认仍建议自动）

`capture_server.py` 新增 `--exposure`（100 µs 单位，0=自动）和 `--gain`，
在 `cv2.VideoCapture` **之前**用 `v4l2-ctl` 写入——**流开着的时候改控制会把服务弄崩**
（2026-10-28 实测：`--set-ctrl` 一发，抓图服务立刻退出，客户端 `ConnectionRefusedError 10061`）。

实测这台 RealSense 彩色：曝光 25→画面均值 18、50→45、100→79、166→109（近似线性）；
当前室内自动曝光稳定在 **~100（10 ms）**，所以钉死 100 几乎不掉亮度，只是去掉自动抖。
再短就过不了 `find_card` 的 `min_brightness=160`，**不加补光灯不要低于 80**。
0.6 rad/s 转动下：10 ms ≈ 3.6 px 像移（仍会糊），停稳时 ≈0.6 px（不影响）。
⇒ 短曝光只是"停稳"之外的保险，不是主力。

### 15.3 笔画太细会被读成别的数字（2026-10-28 深夜实测）

现场症状：卡片摆正、图清晰、卡片宽 177 px，连读 10 次**全部读成 `3`**（真值 `8`），
置信度只有 0.36–0.50。把喂进分类器的 28×28 图打印出来看，字形本身是对的 8，
问题在**笔画粗细**：细记号笔的填充率只有 **0.18**，而训练集（MNIST）笔画粗得多。

| 膨胀遍数 | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| 分类结果 | `3`@0.37 | `3`@0.44 | `8`@0.55 | **`8`@0.79** |

修法（`host/app/vision/digit_reader.py:_stroke_passes`）：填充率门槛从
`<0.16→2 / <0.26→1` 改成 `<0.20→3 / <0.26→2 / <0.34→1`，`MAX_STROKE_DILATE` 2→3。
修完同一张卡 **10/10 全对（`8`，conf 0.77–0.81）**，压力集 44→45/52，场景集与笔色基准不变。

排查顺序（以后再遇到读错，按这个顺序走，别一上来就换模型）：

1. **先看喂进分类器的 28×28 图**（`_scratch/g_0.png` 那种导出）；字形不对 → 查分割。
2. 分割对了但认错 → 查**笔画填充率**（细笔/浅笔），调膨胀遍数。
3. 还错 → 再怀疑角度（旋转 TTA 在压力集上是负收益：31/52 vs 45/52，别设默认）。
4. 最后才考虑换模型。

### 15.4 光轴与像素当量（2026-10-28 实测）

用「原地 ±20°、看卡片框中心怎么动」量过一次（`_scratch/axis_check.py`）：

| 那个停点的实际朝向 | 卡片框中心 x | 框宽 |
|---|---|---|
| 0.0° | 303 px | 120 px |
| +19.7° | 543.5 px | 121 px |

- **像素当量 12.2 px/deg**（= 0.082 deg/px），与代码里 `START_GAIN_DEG_PER_PX = 0.08`
  基本吻合，说明对准用的增益不用改。
- 正对时框中心 **303 px**，离画面正中 320 px 只差 17 px ≈ **1.4°**。⇒ 画面正中就是光轴，
  "居中"是真实测量，不是把卡片硬拧到某个常数上；之前看到的几十像素偏差是狗的实际
  方位角，不是相机偏置。
- 注意：只靠转头**无法**把"光轴"和"卡片本来在哪儿"分开（两者在方程里合并成一项），
  所以这个结论依赖"人把狗摆正"这个前提，只能保证到 1–2°。

## 16. 两个"明明看得见却报没看到"的检测门槛（2026-10-29 离线修复，未上真机）

现场症状都是同一句：**画面里明明有卡片，程序说"没看到数字"**。今晚逐帧查出来是两个
门槛把候选框提前扔掉了，跟识别算法无关。

### 16.1 只对"整体很亮"的帧禁用检测（`find_card`）

`find_card` 里原本有一条护栏，用来防止"整幅画面都是纸"时把纸面噪点当卡片：

```python
median = float(np.median(gray))
dark_fraction = float((gray < median - 40.0).mean())
if dark_fraction < 0.03:      # 旧写法：任何暗部太少就放弃
    return None
```

问题：**棕色纸壳是中灰（中位 132）**，整幅几乎没有"比中位暗 40"的像素，
于是 `dark_fraction = 0.011 < 0.03`，一张对比度 +54 的卡片直接被否掉。实测这个框：

| 候选框 | 面积占比 | 框内中位 | 环带中位 | 结论 |
|---|---|---|---|---|
| (131,129)-(337,244) | 3.2% | **183** | 129 | 本该通过（对比 +54），被 `dark_fraction` 拦在门外 |

改法：护栏只管"整体很亮"的帧，中灰场景放行。

```python
if median > 185.0 and dark_fraction < 0.03:   # 新写法
    return None
```

### 16.2 卡片里的字可以被"压扁"（`_glyphs_in_mask` 的长宽比下限）

`MIN_GLYPH_ASPECT` 原为 0.5（高/宽）。但相机高 0.31 m、卡片在 1.15 m 外，
视线是约 12° 的掠射角，一个手写 "8" 到画面里是 **67×31 px，长宽比 0.46** —— 
被判成"太扁，不是数字"直接丢弃，于是返回 `empty`。这就是"8 只有 200 px 才读对"
（走近、视角变陡、长宽比回到 0.5 以上）的真正原因之一。

改法：**只在一张已确认的卡片内部**把下限放到 0.30；没有卡片的兜底路径仍是 0.5
（没有卡片时，宽扁的亮块多半是杂物）。

```python
# inner / padded 分支（card is not None）
_glyphs_in_mask(..., card=card, min_aspect=MIN_GLYPH_ASPECT)   # 0.30
# 全局 Otsu 兜底分支
_glyphs_in_mask(ink_mask(gray), (0, 0), ...)                   # 默认 0.5
```

### 16.3 排查顺序（"没看到数字"时按这个走）

1. 存帧看画面：卡在不在框里？被画面边缘切了吗？
2. 打印 `find_card`：返回 `None` → 是 16.1 这类门槛问题，不是识别问题；
3. 返回了框但 `extract_glyphs` 是空 → 打印候选团的 area/aspect/edge，对照 16.2；
4. 有 glyph 但读错 → 去 `docs/digit_model.md` 第五节看 28×28 图、笔画填充率、角度；
5. 都正常 → 才是分类器该背的锅。
